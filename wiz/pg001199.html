The Standard General Purpose WIZ Function Block #1

Function block #1 is standard on all WIZes. There will be no variations, so that any program running on a WIZ can count on these functions. The front-end of the function block, as with all functions blocks, is merely 256 read/write registers. On the back-end, they are defined something like this:

Each logical device, such as an adder, multiplier, divider, etc, is a set of registers, and operates independently from all other devices in the function block. For instance, an adder is three registers - two inputs and one output. The output register always contains the sum of the two input registers.

The adder also has a "minus B" input. If you store into it, it will be subtracted instead of added. Only one of either B or minus B must be stored into. The output reflects whichever was most recently stored into.

The Boolean function device has four input registers, A, not A, B, and not B. Only one of each pair is actually used, whichever is the last stored. The device then has three outputs, A or B, A and B, and A xor B, all three of which are always computed. There are 16 possible boolean functions of two variables. As both inputs have a not input, the "A or B" output can generate 4 functions: A or B,  -A or B, A or -B,  -A or -B. Thus each of the three outputs has four different functions, giving a total of 12 functions: A or B, -A or B, A or -B, -A or -B, A and B, -A and B, A and -B, -A and -B, A xor B, -A xor B, A xor -B, and -A xor -B. The last two are duplicates, as A xor -B = -A xor B, and -A xor -B = A xor B. Thus, you have 10 functions of two boolean values. The remaining 6 possible boolean functions are : 0, 1, A, B, -A, -B. The first 4 of these are too trivial to need computation, and the last two are covered by the Inverter device.

When loading the output of any device, the status registers are also updated. These are all 1 bit registers, right justified in a 32 bit word. These flags make for easy testing using the SKIPIF processor register. The FB1 "no-op" register is provided for simply testing a data value. After storing into it the arithmetic flags are set accordingly. All other registers set flags as a result of their output being read.

The above table is just an example, not the final specification. There will probably be many more devices included. There will probably be several adders and multipliers, etc. How many will be determined by simulations.

The main WIZ cycle is always simply the copying of one register onto the processors inter-register buss and another register off the buss. This cycle is not clocked. Instead, all registers must provide a "READY" pulse when they are read from, and this pulse ends the WIZ main cycle. Most registers generate it almost instantly.

But some registers may introduce a delay on the WIZ cycle while that output is made valid, that is, while the device cycles through its computation. For instance, reading a multiplier output register may have to wait for the multiply to finish. In order to provide a way to start the ball rolling sooner, we define that some inputs, generally the last input of each device, will also initiate the device cycle. For instance, as soon as you store into the B input of the multiplier, the device begins the computation (B times A). By starting computations as early as possible and doing other instructions in between the start and the finish, a program can optimize computation speed. As we shall soon see, it is possible to "load up" several or all of the various devices with computations simultaneously.

Once a device starts its computation, storing into any triggering input again before the completion of the computation restarts the computation over again. And storing into any other (non-triggering) input resets the device and terminates any computation in progress. And in any case, loading an output register is always valid, since if nothing else has triggered the computation, the load of the output itself triggers the computation.

For example, the adder A input is non-triggering, and the B and minus-B inputs are triggering. Thus:

XXX => FB1REG #adder-A    / store A, nothing happens.
YYY => FB1REG #adder-B    / store B, adder starts
ZZZ <= FB1REG #adder-SUM  / may wait for adder to finish
Storing B before A creates an extra cycle and is slower than the above code (although produces the same result):
XXX => FB1REG #adder-B    / store B, adder starts
YYY => FB1REG #adder-A    / store A, adder aborts cycle in progress
ZZZ <= FB1REG #adder-SUM  / adder starts again and definitely waits for completion
I will describe each FB1 device briefly. This is not meant to be a full or final specification.

The loop counter device has five registers, a value, an increment, a lower and upper bounds, and an exit address. It also has an "out of bounds" bit which is one if the value is not equal to or within the lower and upper bounds. Whenever you load the value register, you get the current value instantly, and the out of bounds bit is also copied instantly to the out-of-bounds register. No wait will occur. And if the out of bounds bit is one and the exit address register is non-zero, then a <exit address> => RAMXADR is done, that is, the instruction causes a jump to the exit address. Thus, you can load a value, bounds check it, and jump to an exit address, all in one WIZ cycle with no wait for the computation!

AFTER returning the current value, the loop counter initiates its backend cycle. Asynchronously to the WIZ, which may continue along doing other things now, it then adds the increment to the value, and then compares it to the lower and upper bounds registers, setting its internal out of bounds bit accordingly. And anytime the value or either bounds register is stored into, the backend logic recomputes the out of bounds bit (but doesn't increment the value). This allows reads of the loop counter value to always operate instantly, as the computation is always done as a backend operation between reads (during the execution of the code being looped on!).

The loop counter can also be used nicely for subscript calculations with bounds checking.

There will be several loop counters. Simulations will determine how many. Here it is a question not just of speed but of programming convenience. It would be nice to have several loops going at once without having to load and unload a set of parameters.

The Negator, Inverter, and Counter are very simple registers. Load a value into them, load its negative or inverse or successor right back out.

The tally adder is a single register which merely adds all numbers (integers) stored into it. The way to zero it is to load it, negate that value, and add that back to it. A MAC (multiply and accumulate) device could be included also, but may make more sense in a floating point function block.

The nanosecond counter it is merely a counter run at a nanosecond clock rate. It counts to exactly 999,999,999 and then rolls over to zero, exactly once per second. A second register, the counter target, implements an interrupt (to the address in the third register) whenever the nanosecond counter hits that target value.

Cool, huh?

There is more to document, but the above suggests the general plan... Lots of other devices can be thought of. Simulations will determine the most useful before we etch them in stone. Floating point operations may be restricted to a separate function block, or included in FB1 if we want to make them standard. Remember that whatever we put in FB1 becomes standard forever and minimally required in ALL WIZes, so I want to keep it simple. Yet silicon real estate is getting cheaper all the time. Simulations will tell....
