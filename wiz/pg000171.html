WIZ Function Blocks.

From the point of view of the WIZ front-end, a function block is merely a set of (up to) 256 read/write registers of 32 bits each. The WIZ can store into any FB register and load data from any FB register. And that is all there is to a function block -- at least from the point of view of the WIZ front-end.

Independent of the WIZ operation, these blocks of registers then take up a life of their own and may do various things with the data in them. This is referred to as their backend function.

From the point of view of the backend, a function block is a piece of circuitry which "does" various functions for a WIZ. Examples of function blocks would be:

  • An integer arithmetic function block
  • A floating point arithmetic unit
  • An analog I/O block
  • A digital signal processing block
  • A graphics engine
  • A disk controller
  • A modem
  • A radio transceiver
  • Various other custom circuits
  • Another WIZ
There can be up to 256 different function blocks on a single WIZ, each with its own set of up to 256 registers.

Function blocks #0 and #1 are reserved for the WIZ. FB0 is the general purpose register set, also known as the GPREGs. This function block actually has no function other than to provide a set of 256 registers. FB1 provides a number of standard arithmetical and logical functions for the WIZ. It is standard and appears identically on all WIZes.

A function block may continue operating even when no WIZ instruction is referencing it. A function block may have its own independent path to memory. A function block may cause an interrupt to signal when it is "done". A function block may be an entire independently operating WIZ on the same chip.

What are today called IP or "intellectual property" blocks, are typically one of the functions mentioned above, such as a disk controller, a modem, a floating point unit, etc. Produced by different companies who have patent rights and want to protect their investment, inter-operability between various such IP blocks is currently a geo-political engineering nightmare. The WIZ function block provides an absolutely standard interface for such things.

Suppose you have an IP block and maybe some proprietary software to make it go. What is the fewest number of gates you could add to your block that would (a) generalize the block to be useful to others, and (b) run software to make the block a complete hardware/software deliverable. Answer: a WIZ.
 
In other words, the tail wags the dog. Think of it not as
"A WIZ with your IP function block inside it"
but instead as
"Your IP function block with a WIZ wrapped around it!"
Or most simply, it is:
"A WIZ (with your value added capabilities)."
In terms of simplicity, a WIZ is a WIZ is a WIZ. You are marketing just another WIZ, this one with YOUR special value added capabilities. It is compatible to all other WIZs, and can easily be put on the same chip with other WIZs, being a standard WIZ function block itself, or, stand alone on a chip, being a complete WIZ itself.

By gate count, the WIZ is tiny compared to your IP block, so there is very little extra real estate penalty to adding it, and now it can run your software, control the block, meet a standard, and deliver a total package. And this package can be put onto a die with another WIZ. You can keep your hardware patents and protect your software, if that's your game.

In fact, a function block could be SOFTWARE ONLY! Take a standard WIZ and put it on a chip with another WIZ which thinks of it as just another function block. DSP comes to mind. A graphic transformations engine comes to mind. Any proprietary algorithm in ROM comes to mind -- you could deliver an algorithm in hardware as a proprietary on-chip block.

So the WIZ function block architecture gives us IP interoperability and SOC ("system on a chip"), solving both the hardware compatibility issues by providing a de facto standard, and the geo-political legal problem at the same time. Not to mention being a great idea in itself...
