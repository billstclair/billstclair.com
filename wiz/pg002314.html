The Fixup and Software Function Blocks

The MEMXID register allows an inter-memory subroutine call. It makes no assumptions regarding passing arguments, which may be passed in all the usual ways: through gp registers, through the stack, or through specific memory locations.

As a further example of what can be done with the Fixup mechanism, I will now define the MEMFB register and the SOFTWARE FUNCTION BLOCK. This register creates a method for argument passing which I propose as a standard. It is purely software driven, and not required, as the MEMXID register is always also available.

A hardware Function Block has already been defined. On the front end it appears simply as a block of 256 read/write registers. And the act of reading or writing any of these registers may trigger a back-end operation which runs independantly of the WIZ cpu.

A software Function Block is a memory whose first 256 words are likewise accessed as a block of read/write registers. The act of reading or writing any of these registers may likewize trigger a backend operation. In this case, the backend operation consists of executing code found in the same memory. This code may be executed independantly of the WIZ cpu, on another WIZ cpu, or at least as a seperate task on the same CPU.

We define the FB /MEM register, which works very much like the FBREG register, except that where FBREG is followed by two bytes, the FB number and the register number within the FB, the FB /MEM register is followed by 5 bytes, a 4 byte local address (offset) of a memory ID packet, and a single byte register number within that memory.

For example, whereas the following writes GPREG #23 to register #88 in function block #47:

GPREG #23 => FB #47 REG #88
The following writes GPREG #23 to register #88 in SOFTWARE function block <<alpha>>:
GPREG #23 => FB /MEM <alphaPacket> REG #88
where <alphaPacket> is a 32 bit offset in the current memory of a memory-id packet referencing <<alpha>>.

Thus, THE FB /MEM REGISTER MAPS THE FIRST 256 WORDS OF THE ADDRESSED MEMORY.

And just as with a hardware function block, a read or write to or from any of a memory's 256 registers may also trigger a backend operation. In this case, THE BACKEND OPERATION OF ANY REGISTER IN A FBMEM MAPPED MEMORY IS THE EXECUTION OF CODE IN THAT MEMORY. This code is found in bytes beyond the first 256 words of the mapped memory, and its execution is a backend operation which may take place on another WIZ cpu, or as a separate task in the multitasking environment of the current WIZ cpu.

As with a hardware FB register, when a FB /MEM register is accessed, the register may cause a wait if the data in that register is not "ready". Presumably, intelligent programming will take advantage of this architecture to reduce or eliminate wait states.
For example, suppose we have a memory which has code in it to calculate a = bc. The interface is thru registers 4,5 and 6. You store a number into register 4 (b) , the desired power into register 5 (c), and then get the answer from register 6 (a). Register 4 is not a trigger, registers 5 and 6 are. Register 6 must wait until "ready" if not already. The code would be:

gpreg #34 => FB /MEM <mathSubPacket> REG #4   ! Store b
gpreg #35 => FB /MEM <mathSubPacket> REG #5   ! Store c, begin computation
 ...                                        ! ... other instructions may go here
gpreg #36 <= FB /MEM <mathSubPacket> REG #6   ! Get bc, wait if not ready.


Now, let's talk about how this all gets handled: more of THE FIXUP:

The first 256 words of the memory will be mapped to the 256 registers. Actually, we will use 256 x 12 or 3072 bytes to store the registers as we will need 12 bytes or 3 words for each register. If a memory needs less than 256 register (or, in other words, if a subroutine needs less than 256 arguments) it may use less memory: only N x 12 bytes are needed if N is the highest number register used.

For each logical register we use three words of storage. One word is the 32 bit register itself. The second is the offset within the memory of the code to be called whenever that register is loaded from, and the third word is the offset within the memory of the code to be called whenever that register is stored into. Either or both of these two offsets may be zero, in which case no backend function occurs at all (ie, no code is executed).

As the FB /MEM register in FB1 is accessed, like all the MEM registers in FB1, a hardware trap to location zero and the Memory Handler occurs. The Memory Handler can now replace (fixup) the calling instruction with a different instruction or instructions.

For instance, suppose <alpha-packet> is the offset of a packet referencing the memory id <<alpha>>, and that after being loaded into memory, a copy of <<alpha>> exists at absolute RAM address <alpha-addr>. Then <alpha-addr + 12 x 47>, or <alpha-reg47-addr> is the address of the word to load or store for logical register #47 in <<alpha>>, and the data found at <alpha-reg47-addr + 4>, when added to <alpha-addr>, gives the absolute RAM address to call when register #47 is loaded from, we'll call it <alpha-reg47-load-code-addr>, and the data found at <alpha-reg47-addr + 8>, when added to <alpha-addr>, gives the absolute RAM address to call when register #47 is stored into, we'll call it <alpha-reg47-store-code-addr>.

Then, the instruction:

GPREG #34 => FB /MEM <alpha-packet> REG #47   ! Store gpreg #34 into alpha reg #47
can be fixed-up with this new sequence:
<alpha-reg47-addr>            => RAMADR
GPREG #34                     => RAMDATA        ! Store gpreg #34 into alpha reg #47
<alpha-reg47-store-code-addr> => RAMXADR /STACK ! Call corresponding code in alpha
This new code stores GPREG #34 into the copy of <<ALPHA>> at logical register 47, and then calls the code at the address given for handling stores into that register.

Note that execution of <<alpha>> may cause the offset at <alpha-addr + 12 x 47 +4 or +8> to change, which would then in turn cause the third instruction above to change. This is fine, as any such code in alpha will itself go thru a fixup and can then be correctly handled.

Note that this new code is just three fast instructions. We store GPREG #34 into an absolute address, and then CALL another absolute address. Thus, after the FIXUP, the execution is as fast as can be done on a WIZ - no efficiency has been lost - yet a tremendous generalized memory access method is created!

Suppose that <<alpha>> register #4 is not a trigger, and data may be stored there simply by storing it, and no backend function is defined (as b in the above example of a = bc). In this case the call:

gpreg #34 => FB /MEM <mathSubPacket> REG #4   ! Store b
fixups up simply to this code:
<alpha-reg47-addr> => RAMADR
gpreg #34          => RAMDATA                 ! Store b
Thus, a memory register with no backend function has no overhead added when stored into. One just stores into it.

While a STORE into a FB /MEM register generates code which stores first into the register memory address and then calls the corresponding routine, a LOAD reverses the order and calls the corresponding routine first, then loads the memory data. Thus:

FB /MEM REG #47 => GPREG #34
is fixed-up to become:
<alpha-reg47-store-code-addrt> => RAMXADR /STACK
<alpha-reg47-addr>             => RAMADR /READ
GPREG #34                      <= RAMDATA
