Parallelism in the WIZ Architecture

Most current processors must wait for the completion of all instructions before going on to the next. A great deal of complexity is spent on optimizing the instruction flow to allow for parallel execution of several instructions, pipeline execution of instructions, and optimal ordering or reordering of instructions in the pipeline. The WIZ handles and solves this complexity with a simplicity.

The WIZ function block architecture allows a WIZ instruction to start an operation and not wait for its completion. And every function block device, that is, adders, multipliers, logical functions, etc, operates independently and can operate simultaneously. Thus, a WIZ program can easily take advantage of a great deal of parallelism.

The WIZ main cycle is very fast. It is just the time it takes to transfer a 32 bit value across a bus. And as the RAMXADR prefetches the next instruction byte in parallel to the WIZ executing the current transfer, and the RAMADR can increment and prefetch the next word of memory in parallel to the WIZ executing the current transfer, no time is lost between cycles preparing for the next one.

Suppose we have three multipliers, and the six words to load into them are in successive memory addresses. Compare the following two examples, both of which produce identical results:

 
/  EXAMPLE CASE ONE:

   <initial adr of data> => RAMADR

/  load multiplierOne with two data items:
   RAMDATA /INCADR => FB1REG # multiplierOne_A
   RAMDATA /INCADR => FB1REG # multiplierOne_B
/  and get the first product to reg #0:
   GPREG # 0 <= FB1REG # multiplierOne_product

/  load multiplierTwo with two data items:
   RAMDATA /INCADR => FB1REG # multiplierTwo_A
   RAMDATA /INCADR => FB1REG # multiplierTwo_B
/  and get the second product to reg #1:
   GPREG # 1 <= FB1REG # multiplierTwo_product

/  load multiplierThree with two data items:
   RAMDATA /INCADR => FB1REG # multiplierThree_A
   RAMDATA         => FB1REG # multiplierThree_B
/  and get the third product to reg #2:
   GPREG # 2 <= FB1REG # multiplierThree_product

 /  EXAMPLE CASE TWO:

   <initial adr of data> => RAMADR

/  load multiplierOne with two data items:
   RAMDATA /INCADR => FB1REG # multiplierOne_A
   RAMDATA /INCADR => FB1REG # multiplierOne_B

/  load multiplierTwo with two data items:
   RAMDATA /INCADR => FB1REG # multiplierTwo_A
   RAMDATA /INCADR => FB1REG # multiplierTwo_B

/  load multiplierThree with two data items:
   RAMDATA /INCADR => FB1REG # multiplierThree_A
   RAMDATA         => FB1REG # multiplierThree_B

/  and get the first product to reg #0:
   GPREG # 0 <= FB1REG # multiplierOne_product
/  and get the second product to reg #1:
   GPREG # 1 <= FB1REG # multiplierTwo_product
/  and get the third product to reg #2:
   GPREG # 2 <= FB1REG # multiplierThree_product
Note that both these cases have the exact same instructions, but in a different order! In both cases, the third instruction, which loads multiplierOne_B, starts the multiplierOne device computation. And in both cases, when we get to "GPREG # 0 <= FB1REG # multiplierOne_product", the WIZ will stop and wait for the multiply to finish. However, in the second case, we have already loaded the other two multipliers and started them rolling. All of these loads in the second case are "free" (use no time) as they overlap the first multiply. In both cases, the time when the "GPREG #0 <= FB1REG # multiplierOne_product" instruction cycle ends is the same.

But now, if we assume that all three multiplies take the same length of time, then in the second case, after waiting for the first multiplier to finish, the second will also be ready, as it was started just two short WIZ cycles after the first. Thus, in the second case, the instruction "GPREG #1 <= FB1REG # multiplierTwo_product" will NOT WAIT AT ALL as it will already be done. The same is true of the third multiplier product. This is because we had all the multipliers running at once.

Thus, the first case example will take THREE TIMES LONGER to execute than the second case. This is an example of the parallelism possible on the WIZ processor.

Now, let's look at an example comparing a custom hardware datapath combining several functions with the software combination of the same functions on the WIZ. Suppose we want to compute (A+B) x C. Suppose we construct a hardware custom datapath just to do it. This device would have an adder and a multiplier and look like this:
 
A --->|
      |ADDER --->|
B --->|          |
                 |MULTIPLIER  ---> ANSWER (A+B) x C
                 |
C -------------->|

This device would have to be clocked so that the multiplier was started after the adder was finished. And there would probably be a set of latches on the multiplier input to latch the adder output, as a multiplier must have a stable input before it can start.

Now, suppose we didn't build this device but used the existing devices, namely an adder and a multiplier, and combined them with software. The WIZ code would look like this:

FB1REG # adder1_A       <= A
FB1REG # adder1_B       <= B
FB1REG # multiplier1_A  <= C
FB1REG # multiplier1_B  <= FB1REG # adder1_sum
ANSWER                  <= FB1REG # multiplier1_product
Let's examine the timing here. The moment we do "FB1REG # adder1_B <= B", the adder begins computing. The next instruction, "FB1REG # multiplier1_A <= C" is free as it occurs while the adder is adding. The next instruction, "FB1REG # multiplier1_B <= FB1REG # adder1_sum " is the critical one. The WIZ front-end cycle will go into a wait state here. As soon as the adder finishes, it generates a "ready" pulse, and the WIZ inter-register bus, driven by the adder sum, is then latched into the multiplier1_B input and simultaneously triggers the multiplier to start.

How could the hardware custom datapath above be any faster? It also must wait for the adder to generate a ready pulse (or worse yet, be clocked at a fixed time calibrated to the worst case add), and then latch the adder data and start the multiply. While the WIZ front-end cycle is waiting, it is holding the bus ready and gating the adder output register to the multiplier input register, until the ready pulse clocks the multiplier latches and starts the multiply. There is just one level of logic here, which can't be any slower than the hardware datapath.

I have shown the equivalency of the WIZ function block parallelism and a hardware datapath. For the next example, I will show how the WIZ architecture can keep a software pipeline completely full and run as fast as a hardware pipeline.

Suppose we want to compute the sum of the products of A[i] x B[i] over i = 1 to 1000. And suppose we have four multipliers and three adders and a tallyAdder. If we could make a custom pipelined datapath in hardware, it would look like this:
 
A[i] ---->|
          |Multiplier1 ---->|
B[i] ---->|                 |
                            |Adder1 --->|
A[i+1] -->|                 |           |
          |Multiplier2 ---->|           |
B[i+1] -->|                             |
                                        |Adder3 ---> TallyAdder1
A[i+2] -->|                             |
          |Multiplier3 ---->|           |
B[i+2] -->|                 |           |
                            |Adder2 --->|
A[i+3] -->|                 |
          |Multiplier4 ---->|
B[i+3] -->|

This is to be run as a true pipeline, which is different from the above datapath examples in that we do not have to wait for the data to run all the way from the left to the right (from array data to the TallyAdder) on each cycle. We can cycle new array data in continuously, such that all devices are constantly running -- each stage, from left to right, processing the data output of the previous stage.

The WIZ can accomplish the same pipeline in software, AND AT THE SAME SPEED! By loading the outputs of each stage from the inputs of the previous stage in reverse order (right to left), we gain the same effect as a continuously running pipeline. Observe:

 
/ init loop counter to loop 252 times
/  (2 extra to flush the pipeline)

<0> => loopCounter1_value
<1> => loopCounter1_increment
<0> => loopCounter1_lowerBound
<252> => loopCounter_upperBound
<0> => loopCounter_exitAddress

/ zero all 4 multipliers and 3 adders

<0> => multiplier1_B
<0> => multiplier2_B
<0> => multiplier3_B
<0> => multiplier4_B
<0> => adder1_A
<0> => adder1_B
<0> => adder2_A
<0> => adder2_B
<0> => adder3_A
<0> => adder3_B

/ zero the tally

tallyAdder1 => negator
negator => tallyAdder1

/ init the array pointers

loopCounter2_value <= <address of array A>
loopCounter2_increment <= 16

loopCounter3_value <= <address of array B>
loopCounter3_increment <= 16
/ enter main loop

loop:

/ move adder3 sum to tallyAdder
adder3_sum => tallyAdder1

/  move adder1 and 2 outputs to adder3
adder1_sum => adder3_A
adder2_sum => adder3_B

/ move multiplier outputs to adders 1 and 2
multiplier1_product => adder1_A
multiplier2_product => adder1_B
multiplier3_product => adder2_A
multiplier4_product => adder2_B

/ move next 4 words from A and B to the 4 multipliers
loopCounter2_value => RAMADR/READ
RAMDATA /INCADR => multiplier1_A
RAMDATA /INCADR => multiplier2_A
RAMDATA /INCADR => multiplier3_A
RAMDATA /INCADR => multiplier4_A

loopCounter3_value => RAMADR/READ

RAMDATA /INCADR => multiplier2_B
RAMDATA /INCADR => multiplier3_B
RAMDATA /INCADR => multiplier4_B

loopCounter1_value => GPREG #0
out-of-bounds-error => SKIPIF /NONZERO
